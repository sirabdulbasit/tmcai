### Why triage is the leak — root cause located

`server/src/services/triage/triageReasoner.ts:95`

```ts
const cache = new Map<string, CacheEntry>();
const TTL_MS = 60 * 60 * 1000; // 1 hour
```

The triage decision cache is an **in-process `Map` with a 1-hour TTL**. Consequences:

1. Every `pm2 restart` wipes it — and this tree restarts often.
2. A 1-hour TTL means the *same email* is re-reasoned from scratch every hour it is looked at.
3. The gmail feed holds ~2,600 events **total**, yet triage runs ~2,500 times **per day**.
   The feed is not growing by 2,500/day. Nearly all of that spend is re-deciding
   already-decided items.

Average call: **3,189 input tokens in, 141 out.** The system prompt at
`triageReasoner.ts:156-201` is ~1,100 tokens of static instructions, resent in full on every
one of the 487,178 calls. No `cache_control` / prompt caching is applied.

### Four levers, highest value first

1. **Persist the triage decision** on the `feed_event` (or its own table), keyed by
   `dedupHash + contentFingerprint` — the key already exists at `triageReasoner.ts:108`.
   A durable store replaces the 1-hour in-process Map. This alone should remove most of the
   82%. `invalidateReasonerCache()` (line 112) is the existing invalidation seam.
2. **Prompt-cache the static system block** (Anthropic `cache_control`) — ~90% off input
   cost for whatever calls remain after (1).
3. **Cheap pre-filter before the LLM.** `isLikelyAutomated()` already exists and already
   returns AUTOMATED for the broadcast senders — but it does not run on this path (same
   *guard-attached-to-producer-not-value* pattern noted in §3). 23 gmail events are
   `undisclosed-recipients:;` broadcasts that never needed a reasoning call at all.
4. **`criticality_fuse` — 2,082,081 calls.** 4× the triage count for one user. Cheap each
   (~$0.00016) but the call volume is its own problem and has not been investigated. Start
   by finding its call site and asking why it fires ~2M times.

### The meta-pattern worth keeping in mind

Six capabilities now found **built but wired at only one path**: identity spine (populated,
unlinked), LID guard (read paths only), `isLikelyAutomated` (suggestion path only), Rules
(legacy composer only), `saneDueDate`/DEF-017 (one parser only), and now the triage cache
(in-process only). Common cause every time: **a guard attached to a producer rather than to
the value.** When something looks broken, check whether it exists and simply isn't reached.

Second pattern: **two stores for one fact, UI reading the lossy one** — `entities` vs
`wiki_pages` (contacts), JSON blob vs `llm_spend` (spend, was under-reporting by ~half).
